## Dependency interpretation

VoxyServer's Modrinth listing has an empty dependency array, but its published `fabric.mod.json` is authoritative for loader resolution and declares `voxy: "*"`, `fabric-api: "*"`, Fabric Loader >= 0.19.3, and Minecraft `~26.2`. Voxy's metadata requires Fabric API >= 0.91.1, Minecraft exactly 26.2, and Sodium 0.9.1 or 0.9.2. The selected Voxy jar contains a nested server `sodiumprovider` which provides Sodium 0.9.2-alpha.4. This is why the smoke set includes Voxy and VoxyServer, while NusaCore itself does not depend on either.

LuckPerms 5.5.85 Fabric declares Minecraft >= 26.1, Fabric API modules, and bundled `fabric-permissions-api-v0` >= 0.7.0. NusaCore declares `fabric-permissions-api-v0: "*"` as a dependency because `core/permission/PermissionNodes` calls the API directly. The API is also included as a nested jar, so the tree still loads when LuckPerms bundles its own providers. LuckPerms remains an optional server provider: with no provider installed, every NusaCore check falls back to denied, and no command is granted implicitly.

The official Modrinth API response for Voxy Server 1.2.4 records published compatibility only. It does not make Voxy a NusaCore dependency and does not substitute for testing the exact target server image.

## Observed checks

- `gradlew.bat clean build --no-daemon`: PASS (bootstrap slice). Java compilation, resource expansion, jar, and JUnit metadata tests passed.
- Bootstrap artifact inspection test: PASS. `fabric.mod.json` used environment `*`, dedicated server and client entrypoints, no Voxy/Sodium dependency, and the permissions API nested jar. Both entrypoint classes were packaged. No mixins or Voxy/Sodium classes were found.
- Bootstrap dependency smoke: PASS through mod initialization. With LuckPerms 5.5.85, Voxy 0.2.19-beta, VoxyServer 1.2.4, Fabric API 0.161.0+26.2, and NusaCore, Fabric Loader 0.19.5 loaded 61 mods; LuckPerms, Voxy, VoxyServer, and NusaCore initialized without a linkage or dependency-resolution failure.
- Bootstrap smoke: `gradlew.bat runServer --no-daemon` reached NusaCore initialization and the EULA gate, but the process did not exit before the 180-second tool timeout. The generated `run/eula.txt` remains `eula=false`; no EULA was accepted. Voxy emitted missing optional Chunky mixin warnings and continued initialization.
- `/lobby` slice, build and tests (pre-countdown): PASS. `gradlew.bat clean build --no-daemon` passed with 54 JUnit tests in 9 classes and no failures. Coverage was the packaged metadata and entrypoints, permission fallback and provider answers, message mapping, the pure destination rules, the lobby outcome logic, command registration in a real Brigadier dispatcher, the immediate request path (non-player, provider grant and denial, no-provider fallback, permitted, unsafe, unloaded, and missing Overworld), and the hazard classification against the real 26.2 block registry.
- `/lobby` slice, hazard classification: PASS. A wither rose was missing from the hazard list. It has no collision shape, so the shape and fluid rules treated it as open air and a player could be placed inside its damage. `LevelSpawnSurface.isHazard` now includes `WITHER_ROSE`, `END_GATEWAY`, and the lit-state checks for campfires and candles, and the audit against the 26.2 registry is pinned by `LevelSpawnSurfaceTest`. That test bootstraps `SharedConstants` and `Bootstrap` so it reads real block states, real collision shapes, and real state properties, and it proves a wither rose in the feet block or the head block rejects the column while the normal neighbouring column is accepted.
- `/lobby` slice, request path (superseded): `LobbyRequestTest` drove the original immediate-teleport request path with a token player and an in-memory `SpawnSurface`. The countdown slice replaced `LobbyRequest` with `LobbyCountdownService` and replaced this test with `LobbyCountdownServiceTest`, which covers the same start rules through the countdown path.
- `/lobby` slice, in-game behavior (pre-countdown): NOT VERIFIED. Executing `/lobby` in game, a persisted LuckPerms grant, the cross-dimension teleport, and the client-side dimension change were not observed. The unit tests cannot build a `ServerPlayer` or a `ServerLevel`, so `LevelLobbyTarget` (the `TeleportTransition` construction and the live `ServerLevel` view) and the `SourceActions` adapter are covered only by compilation and the server startup check.
- Countdown slice, build and tests: PASS. `gradlew.bat clean build --no-daemon` passed with `BUILD SUCCESSFUL` in 16 s and nine executed tasks; the JUnit XML reports 83 tests in 10 classes with 0 failures, 0 errors, and 0 skipped. New coverage is `LobbyCountdownTest` (18 tests: start bounds, the full-second schedule including that a second shows only after 20 ticks, movement beyond and within the epsilon, looking around, death, dimension change, denial, cancellation after completion, and `Tick`/`State` reporting no feedback for an ended countdown) and `LobbyCountdownServiceTest` (21 tests on a token player through `FakeLobbyPlayer`: start order, duplicate request refused without restarting, permission re-check on later ticks, per-player independence, every cancellation reason, teleport refused at the last second, `cancelAll` on server stop, and 5 s × 20 ticks = 100 ticks to completion). `LobbyCommandTest` was rewritten for the generic command: the tree shape, and that a non-player source gets the player-only message and starts nothing.
- Countdown slice, artifact: PASS. `build/libs/nusacore-0.1.0.jar` (60,839 bytes) contains `LobbyCountdown`, `LobbyCountdownService`, `LobbyCountdownRuntime` with its `ServerPlayerAdapter` and `Sounds`, `Messages`, and `MessageText`, and no `LobbyRequest` class. `fabric.mod.json` is unchanged: environment `*`, server and client entrypoints, no added dependency.
- Countdown slice, server-thread cost: read from the code, not profiled. The tick hook returns immediately unless a countdown is pending (`pendingCount() > 0`), so an idle server does no per-player work. A pending countdown costs one position read, one comparison, and one integer increment per tick, plus one message and one sound packet per second to that player only. There is no timer thread, no `Thread#sleep`, no file or database access, and no chunk load.
- Countdown slice, in-game behavior: NOT VERIFIED. The countdown sound and pitch, the completion sound, the message sequence a real client receives, a live death or dimension change during a countdown, the disconnect and server-stop cleanup hooks, and the teleport refusal path were not observed on a running server. A `ServerPlayer` and a `ServerTickEvents` callback cannot be built in these unit tests, so `LobbyCountdownRuntime` and its `ServerPlayerAdapter` are covered only by compilation and the existing server startup check, which does not reach the EULA gate with a player connected.
- `/lobby` start-failure reporting, build and tests: PASS. A failed start was reported twice: `LobbyCountdownService.start` sent the message through the adapter and `LobbyCommand.execute` sent the same message through `source.sendFailure`. The service now returns the `StartResult` without sending a start failure, and the command is the only reporter; private countdown feedback and cancellation messages still go through the adapter. `gradlew.bat clean build --no-daemon` with Temurin 25.0.4.1+1 passed with `BUILD SUCCESSFUL` in 16 s and nine executed tasks; the JUnit XML reports 89 tests in 10 classes with 0 failures, 0 errors, and 0 skipped. `LobbyCommandTest` now executes the denied, already-pending, missing-Overworld, unsafe-destination, unavailable-player, and non-player paths and counts the message across both layers, so a double report fails. Reintroducing the service-side send for the denied path made `aDeniedPlayerGetsExactlyOneFailure` fail with `player=1 source=1`; reverting it restored the clean build. Artifact: `build/libs/nusacore-0.1.0.jar` (60,693 bytes).
- `/lobby` slice, server startup: PASS. `gradlew.bat runServer --no-daemon` with Fabric API 0.161.0+26.2, Fabric Permissions API 0.7.0, LuckPerms 5.5.85, Voxy, VoxyServer, and the revised jar loaded 61 mods and logged `NusaCore bootstrap initialized: /lobby enabled`, which runs after `CommandRegistrationCallback.EVENT.register` succeeds and after the `LobbyCommand` and `LobbyRequest` construction. No linkage or class-loading error from NusaCore appeared. The process then stopped at the EULA gate; no EULA was accepted and the world was not generated. This confirms the revised classes load in the loader, not that the command runs.
- `/lobby` slice, in-game behavior: NOT VERIFIED. Executing `/lobby` in game, a persisted LuckPerms grant, the cross-dimension teleport, and the client-side dimension change were not observed. The in-JVM provider tests prove the gate reacts to a provider's answer, but a real LuckPerms grant, the server-side chunk load at the destination, and the client following the dimension switch remain unverified.
- Client source compilation passed; client runtime launch, connection, missing-client enforcement, and protocol mismatch behavior are NOT VERIFIED. No payloads, GUI, HUD, or handshake are implemented. The common network package will be added with the real networking slice, not as an unused placeholder.
- Initial checks without `JAVA_HOME` failed because Java is not on PATH. Setting it to the discovered local JDK fixed that environment issue. One split-build attempt timed out at 300 seconds, and the next exposed an obsolete server-only test assertion; after correcting that assertion, `clean build --no-daemon` passed in 12 seconds, with two tests and nine executed tasks.
